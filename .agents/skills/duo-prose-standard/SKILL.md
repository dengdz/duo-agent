# duo-agent 文档写作规范

写足够多来保留契约，然后删除推理过程、重复和装饰。契约是调用者、被调用者、实现者、生产者或消费者依赖的义务、不变量、前置条件、后置条件或兼容性承诺。注释描述代码无法表达的非显而易见契约或理由；不重述代码已经隐含的内容。

本 skill 是指导原则，不是脚本。与 duo-doc-standards 配合使用：后者管位置和层次，本 skill 管质量。

## 输入与排除

需要明确的 `scope`。如果缺失，报告所需输入并停止；不要推断仓库范围或开始访谈。

接受 `mode: automatic | interactive`；默认为 `automatic`。仅在用户明确要求提问或校准时进入交互模式。

`mode` 控制提问，不控制写入权限。审查和审计任务报告发现但不编辑；明确请求的写入、修复或修剪任务应用明确的更改。

始终排除 `target/` 和 Maven 构建产物。不要跟随符号链接进入它。将排除项放在包含 glob 之后，这样后续包含无法重新接纳它。如果请求的范围仅包含构建产物，报告没有符合条件的文件。

生成的 API 目录、快照和固定装置是衍生的。首先编辑所属的源或场景，然后重新生成构件。

## 保留完整命题

编辑前，识别段落中的每个命题。保留每个相关的：

- 行为者和动作
- 条件、时机和顺序
- 模态词如必须、可以、禁止
- 否定保证和异常
- 所有权、副作用、失败模式和后果

仅当每个事实子句都保留且结果更清晰时，才删除形容词、重复和叙述。仅减少字数本身不是改进。

在使用点保留完整的局部契约：调用者或维护者在该处需要的行为、失败、所有权和后果。积极链接到所属文档以获取架构、理由、算法、历史或扩展示例。一个解释有一个主页；基本契约事实可以在本地重复。

保留非显而易见的理由，当省略它可能导致误用或错误的简化。否则说明后果并链接理由主页。

## 各位置的必需覆盖

这不是单向缩短。当代码、类型和结构无法传达下面要求的契约时，添加或恢复文档。当这些事实在本地已经显而易见时，不要添加注释。

- **公共 JavaDoc**：记录调用者可见的返回区别、抛出异常、副作用、所有权、时机、取消和持久性
- **内部注释**：指导非局部结构和明显复杂的局部结构，包括不变量、竞态顺序、所有权、安全边界和意外失败行为。删除控制流叙述和代码重述
- **模块注释**：说明模块的角色、依赖关系、职责和非显而易见的架构选择；链接架构选择到其所属解释
- **测试**：仅解释非显而易见的测试设计——为什么需要固定装置、断言、平台适配、真实入口路径或间接观察。删除演练和清单
- **README**：包括消费者契约：配置、语义、失败、限制、扩展点。引用稳定的用户可见文本；链接所属文档。保留持久的差距和维护者陷阱，不是普通的清理清单
- **示例和配置注释**：解释访问限制、非显而易见的连接或加载顺序、安全立场、重放行为、异常和可能的误用。不要叙述配置已经显示的条目
- **提示词和可见字符串**：将措辞视为行为。检查生成的输出
- **诊断信息**：命名失败的主体或路径、违反的规则，以及非显而易见时的纠正方法。删除内部执行叙述

保留可搜索的机制名称和有意义的模态、时间或否定强调。仅规范化装饰性强调。

## 工作流程

1. 确认范围、模式、当前分支和适用的 AGENTS.md 文件
2. 在判断段落之前阅读所属代码或文档
3. 检查请求的范围，不仅是最大的文件。使用搜索和字数来查找候选者，然后在语义上判断它们
4. 将每个候选者分类为保留、添加、修剪、恢复、重组或延迟。仅当任务授权编辑时才应用明确的更改；不要为了满足删除目标而制造编辑
5. 在衍生构件之前更新所有者。学习新规则后重新检查类似段落
6. 运行狭窄的相关检查、`git diff --check` 和可见字符串的行为测试。验证最终差异不包含 `target/` 路径，并报告任何意外的构建产物匹配，而不是声称干净的排除历史
7. 报告检查的范围、明确的更改、特意保留、延迟的情况和实际运行的检查

## 边界决策

仅当至少两个版本满足完整命题规则但权衡已接受的原则，且本 skill 尚未解决权衡时，案例才是边界的。具有一个保留命题答案的重写不是边界的。

在自动模式下，在授权时应用明确的编辑，并报告真正的边界案例而不提问。不要为了取得进展而削弱命题。

在交互模式下，将类似段落分组在管理原则下。呈现两到三个可行版本，推荐一个，并说明事实或结构差异。不要提供劣质干扰项。

在用户决定后，将原则和版本提炼到示例中，不包括 PR 历史或审查者叙述，并将学到的规则应用于范围内的每个类似段落。

## Java 项目特定指导

### JavaDoc 标准

- **公共 API**：必须有完整的 JavaDoc，包括 `@param`、`@return`、`@throws`
- **包级文档**：每个包应有 `package-info.java` 描述包的职责和主要类型
- **线程安全性**：明确说明类或方法是否线程安全
- **零依赖约束**：在引入任何外部依赖前必须在文档中说明理由（SLF4J API 例外）

### 代码注释原则

- **Why, not What**：注释解释为什么这样做，不是在做什么（代码已经说明了）
- **事件溯源不变量**：涉及 `SessionEvent` 的代码应注释保持的不变量（seq 连续性、surfaceOp 验证等）
- **超时分层**：涉及超时的代码应说明是哪一层的超时（HTTP、LLM、工具执行）
- **工具调用契约**：自定义工具的参数和返回值契约必须清晰

### Markdown 文档

- **代码示例**：必须是可运行的完整示例，包含必要的 import 和错误处理
- **版本信息**：新功能应标注引入版本（`@since 0.2.0`）
- **已知限制**：文档应诚实说明当前限制，不过度承诺

## 验证

- 运行 `mvn compile` 验证 JavaDoc 语法
- 对于 Markdown 链接，检查相对路径的有效性
- 提示词和错误消息的更改应通过相关测试验证输出

## 常见问题

### 何时添加注释？

- 非显而易见的算法或数据结构选择
- 性能考虑或优化
- 并发控制和线程安全保证
- 与外部系统的集成点
- 已知的局限或未来改进方向

### 何时删除注释？

- 重述代码已经清楚表达的内容
- 过时的注释（代码已变但注释未更新）
- 推理过程和决策历史（应移至 Git commit 或设计文档）
- 审查反馈痕迹（"根据 XX 建议修改为..."）

### JavaDoc vs 内联注释？

- **JavaDoc**：公共 API 契约，调用者需要知道的一切
- **内联注释**：实现细节，维护者需要理解的非显而易见逻辑
